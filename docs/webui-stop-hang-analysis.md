# WebUI 停止 (Stop) Button Hang — Root Cause Analysis

> Corrected analysis. Supersedes the earlier (wrong) "peer mailbox stall" reading.
> Authoritative source: user statement — "a past session where a wrap-up message
> (after the 'stucked here' arrow) should be shown, but I hit 停止 on the WebUI
> and the loop hangs. I had to switch to the terminal and hit esc to stop the
> WebUI then re-serve it to continue the loop."
> Screenshot: `.mycc/uploaded/1790754656017_image-1790754582024.png`
> (shows a chat transcript whose last assistant bubble is marked "stucked here...",
> with NO wrap-up message after it).

## Symptom

Clicking the WebUI **停止 (Stop / interrupt)** button during a turn causes the loop
to **hang**: the wrap-up message that should appear after the assistant's last
bubble is never rendered. The user's workaround is to switch to the terminal, press
**ESC** (which stops the WebUI / serve), then **re-serve** to continue the loop.

## What the button does

- WebUI Stop → WS message `{type:'interrupt'}` → `src/serve/serve-ws-handler.ts:117`
  → `agentIO.triggerNeglection()`.
- `triggerNeglection()` (`src/loop/agent-io.ts:350`) sets `neglectedModeFlag=true`
  and aborts the in-flight LLM via the global abort controller.

## The intended (terminal) ESC flow — works

1. ESC → loop returns `STOP`.
2. `stop.ts:112` (mid-execution branch, last role ≠ 'assistant'):
   `startWrapUp(triologue, tools)` — launches a **background wrap-up LLM** and
   stores the result in `wrapUpState.content` via `esc-wrap-up.ts`.
3. STOP returns `PROMPT`.
4. When a **`LineEditor`** is active, the background wrap-up is surfaced by
   `tryDisplayWrapUp(this.activeLineEditor)` (called at `agent-io.ts:893` and
   `agent-io.ts:1017`), which calls `displayLetterBox(content)`.
5. `displayLetterBox` (`src/utils/letter-box.ts:107`) prints the boxed wrap-up AND
   mirrors it to the WebUI through `resultCallback` → `hub.broadcast(...)`
   (wired in `src/serve/activate.ts:32`).

## Root cause — the serve path never displays the wrap-up

In **serve (WebUI) mode there is no `LineEditor`**: the WebUI routes input through
`ServeHub.waitForCardResponse`, so `agent-io.activeLineEditor` is `null`.

`tryDisplayWrapUp` bails out when the editor is null
(`src/loop/esc-wrap-up.ts:228-235`):

```ts
export function tryDisplayWrapUp(editor: LineEditor | null): boolean {
  if (!hasPendingWrapUp()) return false;
  const { content } = wrapUpState;
  if (!content || !content.trim() || !editor) return false;   // ← serve: editor === null
  markWrapUpShown();
  editor.prepareForExternalContentAbove();
  displayWrapUp(content);     // ← the ONLY path that reaches displayLetterBox
  editor.rerender();
  return true;
}
```

Because `editor` is `null` in serve mode:

- `tryDisplayWrapUp` returns `false` **without** calling `displayWrapUp` →
  `displayLetterBox` is never called →
  `resultCallback` is never invoked → **nothing is broadcast to the WebUI**.
- The wrap-up content is generated by the background LLM but is **silently dropped**
  (never marked shown, never delivered). To the user, the chat freezes after the
  last bubble — exactly the reported hang.

The WebUI is only reached by `displayLetterBox` (via `resultCallback`). The
neglection wrap-up is reachable **only through `tryDisplayWrapUp`**, which is
hard-gated on a terminal `LineEditor`. There is **no serve-mode branch** that
broadcasts the wrap-up. That is the bug.

## Why the terminal ESC workaround "fixes" it

Pressing ESC in the terminal while serve is running does **not** call
`triggerNeglection()`; the IPC `neglection` handler checks
`getServeHub().isRunning()` first (`agent-io.ts:253-260`) and calls
`gracefulShutdown()` — tearing serve down and returning to the **terminal**, where
a real `LineEditor` exists. A subsequent ESC/enter then goes through the normal
terminal wrap-up path (which can call `displayLetterBox`). Hence stop-serve →
re-serve "recovers".

## Minimal fix direction (for the peer to implement, pending approval)

The neglection wrap-up must be delivered to the WebUI when serve is running — i.e.
`tryDisplayWrapUp` (or its callers) needs a **serve branch**: when
`getServeHub().isRunning()`, call `displayLetterBox(content)` directly (which
already mirrors via `resultCallback` → broadcast), instead of requiring a
`LineEditor`. Concretely: in `agent-io.ts` at the wrap-up poll sites
(893, 1017) and/or inside `tryDisplayWrapUp`, add:

```
if (hasPendingWrapUp() && getServeHub().isRunning()) {
  markWrapUpShown();
  displayLetterBox(wrapUpState.content);   // mirrors to WebUI via resultCallback
  return true;
}
```

Note also `displayWrapUp`/`tryDisplayWrapUp` require a non-null editor today, so the
serve branch must not depend on the editor argument.
